Migration from application-owned tables ​

Use this guide when moving the shared rendering and interaction behavior out of a consuming application and into @busmap/table. The package should remain an independent UI capability: do not move application data access or domain rules into it.

1. Separate responsibilities ​

Keep these concerns in the consuming application:

  • Fetching, transport clients, DataSources, Redux state, and subscriptions.
  • Domain filtering, authorization, labels, and row projection.
  • Selection state, application actions, and feature/module lifecycle.
  • Decisions about which columns a particular screen shows.

Move only reusable table presentation and behavior into the package:

  • Rendering and table primitives.
  • Pixel/percentage column sizing and resize separators.
  • The included client-side sorting feature and its controls.
  • Optional measured row virtualization.

The package takes prepared rows and typed column definitions as inputs. It does not own a domain model, application store, API client, or theme provider.

2. Add the package and stylesheet ​

Resolve the React peer version and package registry first; see Getting started. Import @busmap/table/style.css once from the application entry.

3. Replace the renderer incrementally ​

Create columns with createColumnHelper, initialize the table with useResizableTable, then replace the application-owned table renderer with ResizableTable. Add TableSortControls only if that screen needs the provided client-side sort UI. Enable virtualize only when justified by the screen's row count and measured performance.

Keep existing row projection and action callbacks in the module. If a custom table rendering pattern is needed, use the exported Table primitives and keep its data mapping in the application.

4. Retire compatibility paths deliberately ​

The original Bus Map application retained Table, ResizableTable, resizableTableFeatures, TableSortControls, SortOrder, and resizeColumnPair re-exports through @busmap/design-system during the extraction. Those exports belong to that application's compatibility layer; they are not part of this package and are not required to consume it.

For independent consumers, import directly from @busmap/table. For the original app, update imports a feature at a time and remove the design-system aliases only after all consumers have moved. Avoid maintaining duplicate implementations or introducing a reverse dependency from the table package to the design system.

5. Validate at both boundaries ​

  • Unit-test application selectors or mapping functions with domain fixtures.
  • Test the table component for rendered data, sorting, resize keyboard interaction, and any row callbacks it supplies.
  • Type-check the consuming workspace and build the application.
  • Check the production CSS bundle includes @busmap/table/style.css.

Run npm test for sizing calculations, npm run lint, and npm run build. Keep consumer-specific integration tests in the consumer repository. Review sizing compatibility changes when migrating old adjacent-pair resize behavior.
