Row selection and context menus: integration from scratch ​

This guide covers two related behaviors in the current Bus Map schedule:

  1. Select a row by clicking it or pressing Enter/Space, and share that selection with other modules.
  2. Open that row's context menu by right-clicking or pressing Shift+F10/the menu key, then invoke an application action.

The examples build a small, generic equivalent for another application with the same architecture: independently mounted React feature modules, shared application packages, and a reusable @busmap/table renderer.

Start with Starter-kit integration if the destination does not yet render a table. This guide is about row behavior, not table-column resizing or module-pane resizing.

What belongs to the table package?

@busmap/table renders rows and forwards getRowProps to their native tr elements. Your application owns selection, menu requests, domain validation, menu content, and downstream actions. Installing the table does not supply a context menu or automatically select a row.

1. Understand the current behavior ​

InputCurrent schedule behavior
Click an unselected rowSelect that route
Click the selected row againClear selection
Enter or Space on a focused rowApply the same selection toggle
Right-click a rowSelect it and open its menu at the pointer
Shift+F10 or ContextMenu key on a focused rowSelect it and open the menu at the row's lower-left corner
Escape or Tab inside the menuClose it and restore focus to the originating row
Click outside the menuFloating UI requests dismissal; the close handler restores row focus
Activate Bus stops listClose the menu and publish a stops-dialog request

Selection starts as null. Right-clicking an already-selected row does not toggle it off. Dismissing a menu does not clear selection.

The schedule uses stable route IDs, so sorting does not change which route is selected. Other subscribers, including the map and timeline presentation, react to the shared selected ID. Selection is runtime state; it is not saved by the separator's Redux user-preferences package.

Concept check: A selected ID is data. A focused row is a DOM element. A menu request describes an interaction. They are related, but they are not interchangeable pieces of state.

2. Establish the architecture and dependencies ​

Use this dependency direction:

text
table feature module -----> shared entity/interaction package
                                      ^
menu feature module ------------------|
details/dialog module ---------------|

table feature module -----> @busmap/table
menu feature module ------> @floating-ui/react + application design system

Do not import the menu module from the table module. They communicate through the shared package, so either can mount independently.

The current application uses:

  • React/React DOM 19.3.1, with compatible React types.
  • The table package's existing TanStack v9 feature API.
  • @floating-ui/react (^0.27.16 in the menu module manifest).
  • Application design-system Menu.Root and Menu.Item wrappers.

Follow the starterkit dependency instructions for compatible versions and workspace installation. Declare dependencies in each consuming module, not only in the repository root.

The example below calls the shared package @example/row-interactions. Replace that illustrative package name with your destination's real workspace name. Export its public API through its package entry and use the destination's existing workspace/build conventions.

Important state-management distinction: the current route selection and menu requests use a small module-scoped external store, not Redux Toolkit. React subscribes with useSyncExternalStore. The Grid separator's Redux preferences are a separate feature. If the destination already has an appropriate Redux DataSource, put these IDs and requests there instead of creating a second source of truth; preserve the behavior described here.

3. Create the shared selection and interaction state ​

This complete example is an adaptation of the current route store and interaction API. It uses generic items rather than bus-specific route fields. Keep this code in a shared application package, not in the reusable table.

ts
// packages/row-interactions/src/index.ts
export type Item = { id: string; name: string };
export type MenuRequest = {
  itemId: string;
  triggerId: string;
  x: number;
  y: number;
};

let items: Item[] = [];
let byId = new Map<string, Item>();
let selectedId: string | null = null;
let menuRequest: MenuRequest | null = null;
const listeners = new Set<() => void>();
const notify = () => listeners.forEach(listener => listener());

export function initializeItems(next: Item[]) {
  const index = new Map<string, Item>();
  for (const item of next) {
    if (!item.id.trim() || index.has(item.id)) {
      throw new Error(`Invalid or duplicate item ID: ${item.id}`);
    }
    index.set(item.id, item);
  }
  items = [...next];
  byId = index;
  if (selectedId !== null && !byId.has(selectedId)) selectedId = null;
  menuRequest = null;
  notify();
}

export const getItems = () => items;
export const getItem = (id: string) => byId.get(id);
export const getSelectedId = () => selectedId;
export const getMenuRequest = () => menuRequest;

export function subscribe(listener: () => void) {
  listeners.add(listener);
  return () => { listeners.delete(listener); };
}

export function selectItem(id: string | null) {
  if (id !== null && !byId.has(id)) throw new Error(`Unknown item: ${id}`);
  if (selectedId === id) return;
  selectedId = id;
  notify();
}

export function openMenu(request: MenuRequest) {
  if (!byId.has(request.itemId) || !request.triggerId.trim() ||
      !Number.isFinite(request.x) || !Number.isFinite(request.y)) {
    throw new Error("Menu requires a known item, trigger ID, and finite coordinates");
  }
  menuRequest = { ...request };
  notify();
}

export function closeMenu() {
  if (!menuRequest) return;
  menuRequest = null;
  notify();
}

Why each part exists ​

  • The array feeds the table; the map validates and looks up entities by ID.
  • A selected ID, rather than a copied row object or array position, remains meaningful after sorting.
  • null explicitly means no selection or no open menu.
  • Menu coordinates are viewport coordinates, matching clientX/clientY and the later fixed-position menu.
  • triggerId identifies where focus should return. DOM elements are not stored in shared state.
  • subscribe returns cleanup so React can unsubscribe on unmount.
  • Getters return the same snapshot until data changes. Do not return a freshly allocated object from a useSyncExternalStore getter on every call.

Treat returned items as read-only data. Apply updates through the shared boundary rather than changing the returned array from a component.

The adaptation intentionally clears an open menu when replacing the item collection, so it cannot retain an invalid item reference. The current Bus Map startup store additionally validates route schedules/stops/coordinates and requires a nonempty route collection; those domain rules are not necessary for this generic example.

Initialize before mounting consumers ​

Once the destination's normal data loading has completed:

ts
import { initializeItems } from "@example/row-interactions";

initializeItems([
  { id: "route-1", name: "University Line" },
  { id: "route-2", name: "Harbor Express" },
]);

This is startup code, not something to run on every React render. The Bus Map equivalent calls initializeTransit(...) at the application boundary.

Why this works: Independently mounted React roots import the same shared package instance. A notification lets each interested root read its new snapshot without importing another feature module.

4. Render the table and integrate selected rows ​

This complete component uses the table's existing API. Import the package CSS once at the application entry as described in Starter-kit integration.

tsx
import { useId, useSyncExternalStore } from "react";
import {
  createColumnHelper,
  ResizableTable,
  resizableTableFeatures,
  useResizableTable,
} from "@busmap/table";
import {
  getItems, getSelectedId, openMenu, selectItem, subscribe, type Item,
} from "@example/row-interactions";

const column = createColumnHelper<typeof resizableTableFeatures, Item>();
const columns = column.columns([
  column.accessor("name", { header: "Name", size: 240, minSize: 120 }),
]);

export function ItemTable() {
  const items = useSyncExternalStore(subscribe, getItems);
  const selectedId = useSyncExternalStore(subscribe, getSelectedId);
  const instanceId = useId();
  const table = useResizableTable({
    columns,
    data: items,
    getRowId: item => item.id,
  });
  const toggle = (id: string) => selectItem(id === selectedId ? null : id);
  const requestMenu = (
    itemId: string, trigger: HTMLTableRowElement, x: number, y: number
  ) => {
    selectItem(itemId);
    openMenu({ itemId, triggerId: trigger.id, x, y });
  };

  return (
    <ResizableTable
      table={table}
      label="Items"
      virtualize
      getRowProps={row => ({
        id: `item-row-${instanceId}-${encodeURIComponent(row.id)}`,
        "aria-selected": row.id === selectedId,
        "aria-haspopup": "menu",
        tabIndex: 0,
        onClick: () => toggle(row.id),
        onContextMenu: event => {
          event.preventDefault();
          requestMenu(row.id, event.currentTarget, event.clientX, event.clientY);
        },
        onKeyDown: event => {
          if (event.key === "ContextMenu" ||
              (event.shiftKey && event.key === "F10")) {
            event.preventDefault();
            const bounds = event.currentTarget.getBoundingClientRect();
            requestMenu(row.id, event.currentTarget, bounds.left, bounds.bottom);
          } else if (event.key === "Enter" || event.key === " ") {
            event.preventDefault();
            toggle(row.id);
          }
        },
      })}
    />
  );
}

How selected-row integration works ​

  1. getRowId makes the entity ID the table's row ID. Never use a sorted array index as the selection key.
  2. getRowProps supplies attributes and handlers for each rendered row.
  3. aria-selected reflects the shared selected ID and activates the table's selected-row CSS.
  4. tabIndex: 0 makes the row keyboard reachable.
  5. Click, Enter, and Space call the same toggle function. Preventing the Space default stops the page from scrolling.

The application does not enable TanStack row-selection state to implement this behavior. Avoid adding a separate TanStack rowSelection state unless you deliberately redesign the ownership contract.

The example's useId prefix prevents DOM ID collisions if multiple table instances show the same items. Current Bus Map has one schedule and uses bus-row-${row.id}. DOM IDs identify focus targets; the shared entity ID remains row.id. Use getElementById for lookup; generated IDs need escaping if used in a CSS selector.

The table supports selected backgrounds through --table-row-selected and an edge indicator through --table-row-selected-edge. Connect them through the destination's theme using the styling guide. Do not rely on a background color alone to communicate selection.

Share selection with another feature module ​

Any React consumer can subscribe without importing the table component:

tsx
import { useSyncExternalStore } from "react";
import { getSelectedId, subscribe } from "@example/row-interactions";

export function SelectedItemSummary() {
  const selectedId = useSyncExternalStore(subscribe, getSelectedId);
  return <p>{selectedId === null ? "No item selected" : `Selected: ${selectedId}`}</p>;
}

The current map uses the same principle to highlight the selected route. This example displays an ID only; a real domain view can also subscribe to entity data and look up its selected entity.

5. Turn a row gesture into a menu request ​

The table component above already includes the two entry paths:

Pointer entry ​

onContextMenu suppresses the browser's native menu, selects the row, and stores clientX/clientY. Opening a menu uses selectItem, not the toggle function, because right-clicking a selected row must leave it selected.

Keyboard entry ​

Shift+F10 and the ContextMenu key have no useful pointer coordinates. Instead, the handler measures the focused row once and uses bounds.left and bounds.bottom. The result is a menu near that row's lower-left corner.

This is an intentional event-time measurement, not separator drag logic. Home/End or Enter on the row do not themselves open a context menu.

Concept check: Publishing a menu request does not render anything by itself. A menu host must be mounted and subscribed to that request.

6. Mount the context-menu view ​

The following complete React component adapts the current one-item menu. It assumes the destination has equivalent design-system Menu.Root and Menu.Item wrappers; in Bus Map they come from @busmap/design-system.

These wrappers must forward refs/HTML props to a native div with role="menu" and a native button with role="menuitem", provide visible focus styles, and style the portaled menu using the destination's theme. This functionality is not exported by @busmap/table.

tsx
import { useLayoutEffect, useSyncExternalStore, type KeyboardEvent } from "react";
import {
  autoUpdate, flip, FloatingFocusManager, FloatingPortal, shift,
  useDismiss, useFloating, useInteractions, useRole,
} from "@floating-ui/react";
import { Menu } from "@busmap/design-system";
import {
  closeMenu, getItem, getMenuRequest, subscribe,
} from "@example/row-interactions";

export function ItemContextMenu({
  onOpenDetails,
}: {
  onOpenDetails: (itemId: string, triggerId: string) => void;
}) {
  const request = useSyncExternalStore(subscribe, getMenuRequest);
  const close = () => {
    if (request) document.getElementById(request.triggerId)?.focus();
    closeMenu();
  };
  const { refs, floatingStyles, context } = useFloating({
    open: request !== null,
    onOpenChange: open => { if (!open) close(); },
    placement: "bottom-start",
    strategy: "fixed",
    middleware: [flip(), shift({ padding: 8 })],
    whileElementsMounted: autoUpdate,
  });
  const { getFloatingProps } = useInteractions([
    useDismiss(context),
    useRole(context, { role: "menu" }),
  ]);
  useLayoutEffect(() => {
    if (!request) return;
    const trigger = document.getElementById(request.triggerId);
    if (!trigger) throw new Error(`Missing menu trigger: ${request.triggerId}`);
    refs.setReference(trigger);
    refs.setPositionReference({
      contextElement: trigger,
      getBoundingClientRect: () => new DOMRect(request.x, request.y, 0, 0),
    });
  }, [request, refs]);

  if (!request) return null;
  const item = getItem(request.itemId);
  if (!item) throw new Error(`Missing menu item: ${request.itemId}`);

  return (
    <FloatingPortal>
      <FloatingFocusManager context={context} returnFocus={false} modal={false}>
        <Menu.Root
          ref={refs.setFloating}
          style={floatingStyles}
          {...getFloatingProps({
            "aria-label": `${item.name} actions`,
            onKeyDown: (event: KeyboardEvent<HTMLElement>) => {
              if (event.key === "Escape" || event.key === "Tab") {
                event.preventDefault();
                close();
              } else if (["ArrowDown", "ArrowUp", "Home", "End"].includes(event.key)) {
                event.preventDefault();
                refs.floating.current?.querySelector<HTMLButtonElement>("button")?.focus();
              }
            },
          })}
        >
          <Menu.Item onClick={() => {
            onOpenDetails(request.itemId, request.triggerId);
            closeMenu();
          }}>
            Open details
          </Menu.Item>
        </Menu.Root>
      </FloatingFocusManager>
    </FloatingPortal>
  );
}

Explain the positioning and focus ​

  • FloatingPortal renders outside the table's scrolling/clipping containers.
  • A virtual reference is a point-like rectangle at the requested coordinates. It positions the menu at the mouse location without creating a hidden DOM anchor. contextElement connects that point to the originating row.
  • strategy: "fixed" matches viewport coordinates.
  • flip() can move the menu to the other side near an edge; shift() keeps it within the viewport with padding.
  • autoUpdate keeps positioning current while the elements are mounted.
  • useDismiss handles outside interaction and Escape dismissal.
  • FloatingFocusManager manages focus on opening. returnFocus={false} avoids competing with the explicit close handler's row focus restoration.
  • The close path deliberately treats Tab as "close and return to the row," matching current Bus Map behavior rather than ordinary Tab-to-next-control.
  • Enter/Space activates the native menu button. The action callback must invoke the destination's real application action; there is no success-shaped no-op.

This is a one-action menu, like the current Bus Map menu. ArrowUp/ArrowDown, Home, and End focus its only button. If adding several actions, implement real enabled-item navigation, such as the destination's existing menu/list-navigation primitive; this handler is not a complete multi-item menu implementation.

If a destination allows row removal while its menu is open, close or reconcile that menu through its state boundary. Focus restoration can only focus a row that still exists. Do not silently display actions for a deleted entity.

7. Wire startup, lifecycle, and the action destination ​

Same React root ​

Render the menu host once alongside the table and supply the real application action:

tsx
<>
  <ItemTable />
  <ItemContextMenu onOpenDetails={openItemDetails} />
</>

Here openItemDetails(itemId, triggerId) is the destination application's function, not an API supplied by the table. It must open or request the intended details UI and arrange focus restoration when that UI closes.

Independent starterkit modules ​

Follow the destination's normal module resolver and registration conventions:

  1. Make the table module depend on the shared interaction package.
  2. Make the menu module depend on that same package, Floating UI, React/React DOM, and its design system.
  3. Mount one menu host using the module's normal createRoot lifecycle.
  4. On module unmount, unmount the React root and call closeMenu(). React subscription cleanup removes that consumer's listener.
  5. Register the menu module with init: true in an existing overlay container. The resolver must map that module name to its actual entry.
  6. Mount the action's destination module too. A menu action cannot display a dialog if nothing consumes its request.

Current Bus Map startup configuration includes:

json
{
  "module-bus-context-menu": {
    "module": "module-bus-context-menu",
    "container": "bus-overlays",
    "init": true
  },
  "module-bus-stops-dialog": {
    "module": "module-bus-stops-dialog",
    "container": "bus-overlays",
    "init": true
  }
}

These are excerpts, not a replacement for the whole module configuration. bus-overlays is a Bus Map container name; use a container that actually exists in the destination shell.

What the current Bus stops action actually does ​

Bus Map's menu calls:

ts
openBusStops({ routeId: request.routeId, triggerId: request.triggerId });

The shared interaction package validates the route, stores a stops request, clears the menu request, and notifies subscribers. The independently mounted stops-dialog module receives that snapshot, looks up the route, and renders the dialog. It carries the trigger ID through so the dialog can return focus.

The generic example uses a callback to avoid imposing a bus-specific details contract on another application. When the destination also uses independent roots, its callback should publish a shared request or existing application topic, not import and call another feature module's component.

8. Virtualization, nested controls, and reuse limits ​

  • Stable IDs: use domain IDs for table keys and selection. Array indexes break selection after sorting or data updates.
  • Virtualization: the current renderer keeps the focused row in its rendered range while focus remains inside that row. Once focus moves into a portaled menu, the row is not guaranteed to stay mounted during arbitrary scrolling. Do not claim universal focus restoration for an offscreen/unmounted trigger.
  • Row focus versus selection: Tab moves focus; it does not select. Moving the pointer over a row does not select it either.
  • Nested buttons/links: the current schedule has no independent action buttons inside these row handlers. If the destination adds them, scope row handlers so clicking/typing in a control does not also toggle the row or replace the control's own context menu.
  • Multiple tables: namespace DOM IDs, but deliberately decide whether they share one selected entity or need separate selection state. useId prevents DOM collisions, not business-state collisions.
  • Touch: this guide does not implement a long-press gesture. Do not assume right-click handlers provide a dependable touch-only action-discovery UI; add an accessible visible action button if needed.
  • Persistence: current selected-row/menu state is in memory only. Do not save pointer coordinates, DOM references, or stale menu requests as user preferences.
  • No blanket architecture claim: this guide documents the current external store and its ownership boundary. It does not convert it to Redux or claim that every destination architecture mandates module-scoped state.

For an air-gapped destination, transfer compatible existing dependency artifacts through the team's offline workflow. Floating UI is used by this menu, unlike the native Grid separator. A table tarball alone does not include the application's menu, shared state package, theme wrappers, or module resolver.

9. Verify the destination ​

Run the destination's existing typecheck, component tests, and build. In this documentation repository, run:

sh
npm run docs:build

The following assertion-only example exercises the public API from section 3. Place it beside the illustrative shared package's source and run it using the destination's existing TypeScript runner (or compile it with its normal build). It requires no new testing framework:

ts
import assert from "node:assert/strict";
import {
  closeMenu, getMenuRequest, getSelectedId, initializeItems,
  openMenu, selectItem,
} from "./index";

initializeItems([{ id: "a", name: "First" }, { id: "b", name: "Second" }]);
assert.equal(getSelectedId(), null);
selectItem("a");
assert.equal(getSelectedId(), "a");
selectItem(null);
assert.equal(getSelectedId(), null);
assert.throws(() => selectItem("missing"));
openMenu({ itemId: "b", triggerId: "row-b", x: 10, y: 20 });
assert.equal(getMenuRequest()?.itemId, "b");
closeMenu();
assert.equal(getMenuRequest(), null);
assert.throws(() => openMenu({
  itemId: "b", triggerId: "row-b", x: Number.NaN, y: 20,
}));

These API assertions do not test React event wiring, positioning, or focus. Use a real browser for the following checks:

  1. Click a row, click it again, and confirm select/clear behavior.
  2. Sort the table and confirm selection follows the entity, not its old index.
  3. Tab to a row; Enter and Space toggle selection without scrolling the page.
  4. Right-click a different row. It becomes selected and its menu opens at the pointer; the native browser menu does not appear.
  5. Press Shift+F10/the menu key. The menu opens near the focused row.
  6. Open near each viewport edge and inside a scrolling table. The menu should remain visible instead of being clipped.
  7. Test Escape, Tab, and outside dismissal. Confirm the current focus-return behavior and that selection remains.
  8. Activate the action. The intended details/dialog appears for the requested entity, not whichever row happens to occupy an old index.
  9. Close the destination UI and verify focus restoration when the trigger still exists.
  10. Unmount/remount the menu module, scroll a virtualized table, and remove data while a menu is open. Verify the destination's explicit lifecycle policy.

Final mental model: The table emits row gestures. The shared application state records the selected entity and menu request. A separate React menu renders that request. Its action crosses the application boundary to a destination view. The reusable table stays independent of all domain rules.
